# TDD 0012: Whole-segment HLS AES-128

- Status: Accepted; implemented for single-file assets
- Created: 2026-10-04
- Updated: 2026-10-04
- Related ADRs: [ADR 0001](../adr/0001-use-fragmented-mp4-for-media-segments.md)
- Related designs: [TDD 0009](0009-common-encryption-and-drm.md) (the `cbcs` mode this sits beside), [TDD 0011](0011-muxed-hls-audio.md)

## Summary

The mapper can give an answer an `hls_aes128` object: a 16-byte key and the URI players fetch it from. segmentor then encrypts every HLS media segment whole with AES-128-CBC, as RFC 8216 defines for `METHOD=AES-128`, and the playlists name the key. It protects content without a DRM vendor, which is what nginx-vod-module's "HLS AES-128" does. It is HLS only.

## Context

[TDD 0009](0009-common-encryption-and-drm.md) covers studio-grade DRM: `cbcs` sample encryption, key IDs, `pssh` boxes, and licence servers. Many deployments want something simpler: stop casual downloading and hotlinking, behind their own authenticated key endpoint, with no DRM vendor. HLS has a mode for it: the whole segment is one AES-128-CBC message, and the playlist says where the key is. It is not DRM (the key is delivered to the player in the clear, over TLS), and it is not sample encryption: the `moof` is encrypted along with the media.

## Goals

- A single-file asset whose HLS media segments are encrypted whole, playable by any HLS client that supports `AES-128`.
- The mapper supplies the key and where players fetch it. segmentor does not serve keys.
- Deterministic output, so immutable URLs, ETags, ranges, and CDN caching work unchanged.

## Non-goals

- Serving the key. Players fetch it from the URI the mapper names, which is the operator's authenticated endpoint. A route in segmentor that returned keys would put a secret behind whatever protects the origin, which is usually less than a key service has.
- DASH. It has no whole-segment mode, so an `AES-128` asset answers `404` on `/dash/`.
- I-frame playlists, adaptive (multi-file) assets, and clip sequences. See Limits.
- Key rotation, and an explicit `IV` attribute.

## Design

### Wire format

```json
"hls_aes128": { "key": "2b7e151628aed2a6abf7158809cf4f3c", "key_uri": "https://keys.example.com/movie/1" }
```

`key` is 32 hex digits. `key_uri` is written into the playlist as the `URI` attribute: 1 to 2048 characters without quotes or control characters, absolute or relative (a relative URI resolves against the playlist). An answer that sets both `hls_aes128` and `encryption`, that sets `hls_aes128` on renditions or clips, or that has a malformed field is rejected. The reason names the field, never the key.

### The playlists

```text
#EXT-X-MAP:URI="init.mp4?v=..."
#EXT-X-KEY:METHOD=AES-128,URI="https://keys.example.com/movie/1"
#EXTINF:6.000,
segments/0/media.m4s?v=...
```

The `EXT-X-KEY` line comes **after** the `EXT-X-MAP` line. A key applies to the initialization sections that appear between it and the next key (RFC 8216, 4.3.2.4), so the init segment is sent clear: it holds codec configuration, not media. There is no `IV` attribute, so each segment's IV is its media sequence number as a 128-bit big-endian integer (RFC 8216, 5.2). Playlists start at `EXT-X-MEDIA-SEQUENCE:0`, so segment `n` has IV `n`. This applies to the muxed stream, the separate video, and the separate audio renditions alike.

### The segments

A segment is its `moof`, `mdat` header, and payload, padded with PKCS#7 (always at least one byte, so a multiple of 16 gains a block) and encrypted as one CBC message under the key and the segment's IV. The pending-encryption step TDD 0009 added for `cbcs` does the work: the server reads the segment's byte ranges into memory, encrypts off the async workers, and serves the finished bytes under a job slot, so `HEAD` and byte ranges work from the encrypted bytes. The encrypted length is not the clear length, so `Content-Length` and ranges describe the encrypted bytes.

### The version

The key and its URI enter the URL version, so changing either gives new URLs and a CDN never keeps old segments under a new key.

## Security and limits

- The key is a secret in the mapper answer, like `cbcs` keys: the mapper must be reached over `https` with its bearer token. `Debug` output and every error message omit it, and the version contains only its SHA-256.
- The key travels to every player. Anyone who can fetch the key URI can decrypt the stream, so that endpoint is where authorization belongs (a signed URL, a token, a cookie). That is the mode's whole security model; for studio content use `cbcs`.
- Segments are held in memory while they are encrypted, as `cbcs` segments are, and count against the same job slots and `limits.max_segment_bytes`.

## Limits of this stage

- **Single-file assets only.** Adaptive assets would need the playlists they re-render to carry the key, and sequences need a key per clip transition. The mapper is told so: it gets an error naming the field.
- **No I-frame playlist.** The fragments of an I-frame playlist are not encrypted here, so none are offered, and the endpoints answer `404`.
- **Not tested on Safari.** `AES-128` over fragmented MP4 is in Apple's authoring specification and hls.js; the stream is checked with FFmpeg's HLS client, which fetches the key, and with OpenSSL.

## Testing

- The cipher against OpenSSL, byte for byte, for several segment numbers and lengths including a multiple of 16.
- Every segment of the muxed, video, and audio streams, decrypted with OpenSSL under the segment-number IV, equals the clear segment of the same asset.
- The playlists: `EXT-X-KEY` after `EXT-X-MAP`, no `IV`, the init segment clear, no I-frame stream in the master.
- `HEAD` and byte ranges on an encrypted segment; DASH and I-frame requests answer `404`.
- The answers the mapper may not give are rejected without echoing the key.
- FFmpeg's HLS client fetches the key from the URI and decodes every frame, and does not with another key.
- Four mutations (IV off by one, key before the map, no padding block for aligned data, muxed segments left clear) are each caught.

## Rollout

Additive. Assets without `hls_aes128` are unchanged.

## Open questions

- Key rotation: a new `EXT-X-KEY` every N segments, with a key per period. It belongs with the `cbcs` key-rotation work.
- Whether to also serve the key from segmentor behind the same viewer authorization as segments, once [TDD 0007](0007-viewer-authorization.md) lands.
